Blocking severity

The three things we would fix first, in order:

  1. Give every form field a real label. Ten fields on your enquiry form have none. A screen-reader user reaches your form and hears "edit text, blank" ten times. They cannot complete it. This is the single highest-impact fix on the page.
  2. Add headings. The page currently has none at all. Heading navigation is the primary way screen-reader users skim a page; without it they must read every word in order.
  3. Fix the navigation contrast. Your main menu renders at 2.52:1 against its background where 4.5:1 is required. This affects every user in bright light, not only those with low vision.

Severity is judged on user impact, not just standard conformance. Blocking = a user cannot complete a core task. Serious = significant barrier with a workaround. Moderate = degraded experience.

Findings

1. Form fields have no labels

Blocking10 instances

WCAG 3.3.2 Labels or Instructions (Level A) · also 4.1.2 Name, Role, Value

What happens. Ten inputs on the enquiry form — including name, email and the subject checkboxes — have no <label>, no aria-label, and no programmatic association of any kind. A screen reader announces each one as an unlabelled edit field. The user has no way to know what to type where.

Evidence

  • div > input[type="text"] — no label, no placeholder (×3)
  • div > input[type="checkbox"] — no label (×6)
  • input[name="email"] — no label

Fix

<!-- Before -->
<div>Your email</div>
<input type="text" name="email">

<!-- After -->
<label for="email">Your email</label>
<input type="email" id="email" name="email" autocomplete="email">

A placeholder is not a label — it disappears the moment the user types, and many screen readers do not announce it at all.

2. The page contains no headings whatsoever

BlockingWhole page

WCAG 1.3.1 Info and Relationships (Level A) · also 2.4.6 Headings and Labels

What happens. We queried the page for every heading level h1–h6 and got an empty result. Text that looks like a heading is styled with font size alone. Screen-reader users navigate long pages by jumping between headings; with none present, the entire page is one undifferentiated block they must listen to linearly.

Evidence

  • Heading outline: (empty — 0 headings found)
  • No <main> landmark either, so "skip to main content" has nothing to target

Fix

Mark the visual hierarchy up semantically: one <h1> naming the page, then <h2> for each major section, <h3> beneath those. Do not skip levels. Wrap the primary content in <main>. This is usually a same-day change and it is the highest-value structural fix available.

3. Navigation text fails minimum contrast

Serious4 instances

WCAG 1.4.3 Contrast (Minimum) (Level AA)

What happens. The primary navigation renders grey-blue on light grey at a measured ratio of 2.52:1. WCAG AA requires 4.5:1 for normal-size text. This is below the threshold by a wide margin and affects anyone with reduced contrast sensitivity, anyone on a phone outdoors, and anyone on a cheap monitor.

Evidence

  • li > a "About" — 2.52:1 — rgb(138,148,168) on rgb(233,233,237)
  • li > a "Academics" — 2.52:1
  • li > a "Admissions" — 2.52:1
  • li > a "Visitors" — 2.52:1

Fix

Darkening the link colour to #4a5568 against the same background reaches 5.1:1 and passes. No layout change required — it is a single CSS value.

4. Grouped checkboxes have no fieldset or legend

Serious6 inputs, 1 group

WCAG 1.3.1 Info and Relationships (Level A) · also 3.3.2

What happens. Six checkboxes (major_cs, major_econ, major_eng, major_phy, major_psy, major_sp) together answer one question — which subjects interest you. Nothing in the markup says they belong together. A screen-reader user hears six disconnected checkboxes with no idea what question they are answering.

Note: automated scanners do not catch this. It was found in manual review.

Fix

<fieldset>
  <legend>Which subjects are you interested in?</legend>
  <label><input type="checkbox" name="major_cs"> Computer Science</label>
  <label><input type="checkbox" name="major_econ"> Economics</label>
  ...
</fieldset>

5. Images missing alternative text

Serious3 instances

WCAG 1.1.1 Non-text Content (Level A)

What happens. Two images have no alt attribute at all, and the site logo has alt="au123456789.gif" — the filename, which tells the user nothing.

Evidence

  • div > img — slide1.jpg, no alt attribute
  • #captcha > img — captcha.png, no alt attribute — see also finding 6
  • #logo — alt="au123456789.gif"

Fix

Describe the image's purpose in context, not its appearance. The logo should be alt="Accessible University — home" since it is also a link. Purely decorative images take alt="" so screen readers skip them silently.

6. Image-only CAPTCHA with no accessible alternative

Blocking1 instance

WCAG 1.1.1 Non-text Content (Level A)

What happens. The form is gated by a visual-only CAPTCHA image with no text alternative and no non-visual route past it. A blind user cannot submit the form. At all. This is a hard stop, and it sits in front of your enquiry conversion.

Fix

Replace image CAPTCHAs with a non-visual method: a server-side honeypot field, a time-to-submit check, or a modern privacy-preserving challenge that offers an audio and a cognitive alternative. If a CAPTCHA must stay, WCAG requires alternatives in more than one modality.

7. Touch targets below the 24×24px minimum

Moderate8 instances

WCAG 2.5.8 Target Size (Minimum) (Level AA — new in WCAG 2.2)

What happens. The form's checkboxes render at 13×13 CSS pixels. WCAG 2.2 sets a 24×24 minimum. Users with tremor, limited dexterity, or simply large fingers on a phone will mis-tap repeatedly.

This criterion is new in WCAG 2.2 and most audits published before 2024 do not test for it.

Fix

Wrap each control in a label with padding so the whole hit area is at least 24×24, or scale the control with width:24px;height:24px. Padding counts toward the target size.

8. Link text does not describe its destination

Moderate3 instances

WCAG 2.4.4 Link Purpose (In Context) (Level A)

What happens. Three links read "click here". Screen-reader users commonly pull up a list of all links on a page to navigate; that list here reads "click here, click here, click here".

Fix

Rewrite so the link text alone makes sense: "click here to see our courses" becomes "see our courses" as the link.

9. Page language not declared

Moderate1 instance

WCAG 3.1.1 Language of Page (Level A)

What happens. The <html> element has no lang attribute, so assistive technology guesses the pronunciation rules. English read with a French synthesiser is close to unintelligible.

Fix

<html lang="en-GB">

One attribute. Thirty seconds. It is on the list because it is free to fix and genuinely matters.

10. Data table has no header cells

Moderate1 table, 4 rows

WCAG 1.3.1 Info and Relationships (Level A)

What happens. The enrolment table uses <td> throughout with no <th>. Screen readers announce cell contents without the column context, so a user hears "1,240" with no idea which year or category it belongs to.

Fix

<th scope="col">Year</th>   <!-- column headers -->
<th scope="row">2026</th>  <!-- row headers -->

What we tested, and what we did not

Tested: automated checks across the full DOM (contrast computed against resolved background colours, accessible-name computation, label association, heading structure, ARIA reference integrity, target sizing, landmark structure), plus manual review of tab order, reading order, heading outline, and form grouping and error handling.

Not tested in this sample: screen-reader behaviour in JAWS/NVDA/VoiceOver, content behind authentication, PDF documents, and colour contrast over background images — which we deliberately skip rather than guess at. A full Compliance Pack covers the first three.
